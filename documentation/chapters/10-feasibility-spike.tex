\chapter{Feasibility Spike}

\section{Purpose}

The feasibility spike focuses on the riskiest architectural assumption in this checkpoint: that
nopCommerce can remain the commerce core while durable omnichannel integration is added around
it. The spike therefore asks whether the current codebase has credible seams for the first
target evolution step: recording an order, creating durable integration work, and processing
that work outside the customer checkout path.

This chapter is intentionally scoped. It does not claim that the outbox, Integration Worker,
RabbitMQ queues, warehouse adapter, retry policy, dead-letter queue, or support dashboard are
already implemented. Those elements are part of the proposed target architecture. The spike
checks whether they can be introduced without a rewrite and identifies the smallest useful
implementation slice for the final delivery.

\section{What Was Tested}

The spike used source-code inspection and report compilation rather than a full runtime
implementation. This was appropriate for the checkpoint because the main risk was architectural
fit: whether nopCommerce has a stable order-placement seam and background execution mechanism
that can support the proposed asynchronous integration path.

\section{What Worked}

The main result is that the first target step is feasible without decomposing nopCommerce.
The order-placement path already has a clear point where integration work can be created after
the order exists. The current \texttt{OrderPlacedEvent} is not durable enough for Scenario C,
but it identifies the correct domain moment: the order has been accepted and can now be
propagated to fulfillment.

The scheduled-task infrastructure is also useful. It already supports background execution,
interval checks, and locking to avoid overlapping runs. This makes it a credible mechanism for
a first outbox publisher in the final demo. A production version could later move that work to
a separately deployable Integration Worker, but a scheduled task is sufficient for proving the
architectural tactic in a focused assignment spike.

The stock and shipment models provide enough baseline data to build projections. Existing
inventory records already distinguish stock quantity from reserved quantity, and stock history
records can explain local changes. Shipment records already carry tracking and lifecycle dates.
The missing part is not the basic commerce model; it is integration metadata: source system,
last confirmed time, stale state, retry count, idempotency key, failure reason, and
reconciliation state.

\section{What Did Not Work Yet}

The current implementation does not contain a transactional outbox, RabbitMQ integration,
warehouse adapter, shipping adapter, retry scheduler, dead-letter table, or operator-facing
integration dashboard. Therefore, the current codebase cannot yet demonstrate the mandatory
Scenario C pressure point at runtime. If the warehouse is unavailable today, there is no
standard durable fulfillment command that remains pending and retries automatically.

The in-process event publisher is specifically not sufficient as the external integration
mechanism. It awaits consumers in the same process and logs failures, but it does not preserve
failed work as a business-visible state. This confirms the need for ADR 2 rather than replacing
it.

\section{Smallest Implementation Slice for the Final Demo}

If implementation time is limited, the final demo should not attempt the whole target
architecture. The smallest useful slice is:

\begin{enumerate}
    \item Add an \texttt{OmnichannelIntegrationTask} or outbox table with order ID, message
    type, payload, status, retry count, next attempt time, correlation ID, idempotency key,
    and last error.
    \item Create one outbox record when an order is accepted. The record should represent
    \texttt{FulfillmentRequested}.
    \item Add a scheduled task that reads pending records and calls a warehouse simulator or
    stub endpoint.
    \item Make the simulator return success, timeout, and failure modes through configuration.
    \item On failure, update the task to retrying or failed with a visible error. On success,
    mark it accepted or recovered.
    \item Add a minimal admin or log-based view showing pending, retrying, failed, and
    recovered states for one order.
\end{enumerate}

This slice directly demonstrates QA Scenario 1: checkout records the order, warehouse failure
does not block the customer path, the fulfillment request is retained, and recovery is visible
after the dependency becomes available again. Shipping, inventory conflict handling, and
dead-letter intervention can remain documented target behaviour if there is not enough time to
implement them.
